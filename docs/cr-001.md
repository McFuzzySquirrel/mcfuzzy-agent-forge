Change Request: Make PRD Quality Gates Automatic and Require an Existing PRD for Build Execution

Context

MyForge currently has several points where the user is asked to make decisions that can either be determined mechanically from the project artifacts or that allow the build pipeline to proceed without sufficient PRD review.

Two related behaviors have emerged:

1. PRD decomposition is unnecessarily opt-in

ADR-002 introduced forge-decompose-prd as an opt-in, manually invoked skill. A user had to recognize that their PRD was large and separately run forge-decompose-prd after forge-build-prd completed.

ADR-018 subsequently added a pause in forge-auto-build asking whether the user wanted to decompose a qualifying PRD before continuing to the review gate.

However, the decomposition decision is already deterministic. forge-decompose-prd has objective qualifying criteria:

    15+ functional requirements, or
    3+ implementation phases.

These criteria are calculated directly from the PRD. Asking the user to decide whether a mechanical threshold has been reached adds friction without providing meaningful additional safety.

Decomposition is also non-destructive:

    The original docs/PRD.md is preserved.
    The decomposed representation is generated as docs/product-vision.md plus docs/features/*.md.
    Downstream tooling such as forge-build-agent-team and project-orchestrator already detects and works with either a monolithic PRD or the decomposed layout.

2.

forge-auto-build

can currently bypass meaningful PRD review

The existing prompt playbook and README present MyForge largely as a flat sequence of steps covering bootstrap, PRD generation, decomposition, team generation, model assignment, execution, feature work, and orchestration.

Two fast-path meta-skills exist:

    forge-bootstrap-project - chains PRD generation, review, agent-team generation, review, and optional model assignment, stopping before execution.
    forge-auto-build - chains PRD generation, agent-team generation, optional model assignment, and build execution behind a single pre-flight confirmation.

This means forge-auto-build can take a bare one-line idea, generate a PRD, and proceed through team generation and a complete build after only one confirmation gate.

This under-weights the PRD as the highest-leverage and most expensive-to-correct artifact in the pipeline. A user in a hurry could effectively type “GO” once and receive a fully built project from a thin, unreviewed PRD.

The flat step structure also makes the required starting state unclear. For example, it is not immediately obvious whether forge-auto-build requires an existing PRD or creates one itself.

Decision

1. PRD decomposition becomes automatic

PRD decomposition will no longer require user opt-in when the existing qualification criteria are met.

forge-build-prd gains a new closing step:

Step 5 - Check Decomposition Criteria

This step runs immediately after the user confirms that the PRD is ready and it has been saved to docs/PRD.md.

The behavior is:

    Evaluate the existing decomposition criteria.
    If the PRD qualifies, automatically invoke forge-decompose-prd.
    If the PRD does not qualify, retain the monolithic docs/PRD.md and report that decomposition was not required.
    Do not ask the user whether they want decomposition when the objective criteria are met.

The qualification threshold remains unchanged:

    15+ functional requirements, or
    3+ implementation phases.

This change only removes the unnecessary manual confirmation step.

forge-decompose-prd remains independently invokable so that it can still be used for older PRDs, PRDs modified after generation, or users who explicitly want to decompose a document that does not meet the automatic threshold.

Users may still choose to edit the PRD to change its structure or scope before continuing. Automatic decomposition does not remove the user’s ability to control the artifact; it simply removes a redundant decision about a deterministic mechanical check.

2.

forge-bootstrap-project

is retired

forge-bootstrap-project is retired and its skill directory is removed.

Its useful behavior is not lost:

    Its idea-confirmation pattern is reused by forge-auto-build-prd.
    Its PRD review checklist is reused as part of the PRD-generation flow.

Team generation remains owned by forge-build-agent-team, whether invoked directly or as part of forge-auto-build.

3.

forge-auto-build

requires an existing PRD

forge-auto-build will no longer generate a PRD.

Its pre-flight check must find one of the following:

    docs/PRD.md
    docs/product-vision.md together with docs/features/*.md

If neither representation exists, forge-auto-build stops immediately and directs the user to first run:

    forge-auto-build-prd, or
    forge-build-prd.

It must not fall back to interviewing the user for a one-line idea.

This establishes a clear boundary:

PRD creation is a deliberate stage; build execution is not allowed to implicitly create its own requirements.

4.

forge-auto-build

stages are simplified

With PRD creation removed, the remaining stages are:

Stage 1 - Build Agent Team

forge-build-agent-team

Stage 2 - Assign Models (optional)

forge-assign-models

Stage 3 - Build Execution

forge-orchestrate-build or forge-workflow-engine

The PRD is therefore an explicit prerequisite rather than an implicit side effect of forge-auto-build.

5. Downstream references are updated

All documentation and launcher flows must reflect the new lifecycle.

This includes:

    workflow-orchestrator “when to use” guidance.
    plugin/plugin.json skill listings.
    forge-launcher Step 6 and Step 8 flows.
    Both Bash and PowerShell launcher implementations.
    Prompt playbook and README documentation.
    References to forge-bootstrap-project.

The launcher behavior becomes:

    If no PRD was captured during Step 6, queue forge-auto-build-prd.
    If a PRD was captured, queue forge-auto-build against the existing PRD.

Resulting MyForge Lifecycle

The resulting model is intentionally more explicit:

Idea → PRD creation/review → automatic decomposition check → agent team → optional model assignment → build execution

The important distinction is that the pipeline now separates artifact creation and validation from execution.

A user can still use fast paths, but fast paths no longer allow execution to implicitly manufacture the artifact that governs the build.

At the same time, deterministic mechanical checks no longer interrupt the user with decisions they cannot meaningfully improve.

Rationale

This change establishes two complementary principles:

Automate deterministic decisions

If a decision can be calculated objectively from an artifact and the operation is non-destructive, MyForge should perform it automatically rather than asking the user to confirm the calculation.

PRD decomposition is an example of this principle.

Require deliberate human ownership of high-leverage artifacts

If an artifact defines what is going to be built, the user should explicitly enter the execution pipeline with that artifact available for review.

The PRD is therefore a quality gate, not merely an intermediate file generated on the way to execution.

Together these principles reduce unnecessary interaction while increasing the quality and predictability of autonomous builds.

Acceptance Criteria

    forge-build-prd automatically evaluates the existing decomposition criteria after saving a confirmed PRD.
    A qualifying PRD automatically invokes forge-decompose-prd.
    A non-qualifying PRD remains monolithic and the result is reported.
    No decomposition opt-in question is presented for qualifying PRDs.
    The 15+ requirement / 3+ phase threshold remains unchanged.
    forge-decompose-prd remains independently invokable.
    forge-bootstrap-project is removed.
    Its useful review and confirmation behavior is incorporated into the appropriate surviving flow.
    forge-auto-build no longer generates a PRD.
    forge-auto-build requires either docs/PRD.md or the decomposed PRD representation.
    forge-auto-build stops with clear guidance when no PRD exists.
    forge-auto-build no longer falls back to a one-line idea interview.
    forge-auto-build stages are reduced to team generation, optional model assignment, and execution.
    Launcher Bash and PowerShell flows are updated.
    workflow-orchestrator, plugin/plugin.json, README, and prompt playbook references are updated.
    Existing downstream consumers continue to support both monolithic and decomposed PRD layouts.

The key architectural idea I think this captures is “automate mechanical gates, preserve human gates.” Decomposition is mechanical, so automate it; deciding that the requirements are actually good enough to build is human, so keep that as the meaningful gate. That also makes forge-auto-build much cleaner conceptually: it is an execution fast-path, not a requirements-generation fast-path.
